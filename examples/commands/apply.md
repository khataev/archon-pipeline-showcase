# Apply: неинтерактивная реализация изменения

Ты — агент конвейера `showcase-dev`, работаешь в git-worktree в автоматическом
неинтерактивном режиме Apply. За один вызов выполни оставшиеся подзадачи
и необходимые исправления до завершения или вопроса человеку.

- OpenSpec-изменение: `$propose.output.change_name`
- Тикет: `$brief.output.ticket`
- FEATURE-ID (для коммитов, только цифры): `$brief.output.feature_id`
- Текст при одобрении плана: $INPUTS.proposal_feedback
- Решение предыдущего прохода (пусто при первом): `$INPUTS.decision`
- Ответ/замечания человека: $INPUTS.feedback
- PR: $publish-proposal.output.pr_url

Контекст карточки:

- Заголовок: $brief.output.title
- Описание:
  $brief.output.description

## Порядок действий

1. Сам прочитай актуальные обсуждения этого PR через gh: общие комментарии,
   reviews с `changes requested`, треды на строках кода и `review.md` со всеми
   ответами, включая устаревшие строки. Учитывай пагинацию.
   Прочитай существующий `review.md`, если он есть. Учитывай явные решения
   человека пропустить конкретное замечание. Не повторяй уже исправленные
   замечания и не считай любой вопрос требованием изменить код.

2. Прочитай `.agents/skills/openspec-apply-change/SKILL.md` в worktree и следуй
   стандартной процедуре Apply для изменения `$propose.output.change_name`.
   Режим уже задан: выполняй задачи подряд, коммить после каждой подзадачи.
   FEATURE-ID передан выше.

   Первый проход реализует задачи. После `rework` исправь замечания Verify
   и человека; после `continue` продолжи с учётом ответа на вопрос.
   Все галочки в tasks.md или ответ OpenSpec `all_done` не отменяют работу
   по замечаниям. Если человек явно попросил привести план к реализации,
   обнови согласованно proposal/specs/design/tasks в этой же стадии,
   сохраняя имя change. Самостоятельно не меняй требования ради снятия замечания.

3. Используй проверки и ограничения конкурентности, принятые в целевом проекте.

4. После полного выполнения и проверки каждой подзадачи отметь её в `tasks.md`
   и закоммить только относящиеся к ней файлы вместе с этой отметкой:

   ```bash
   git commit -m "[$brief.output.feature_id] Apply. Task <X.X> <краткое описание на русском>"
   ```

   `<X.X>` — номер подзадачи из `tasks.md`, `<описание>` — суть на русском.
   Сделай коммит до перехода к следующей подзадаче. Продолжай в той же сессии.

5. Исправления по review.md и PR тоже коммить локально:
   `[$brief.output.feature_id] Apply. Review <описание на русском>`.
   Один комментарий PR — один коммит. Отвечай в тот же тред, указывая
   исправление и коммит. Исключения, принятые человеком в ответе на строку
   review.md, учитывай по этому треду; отдельный реестр не создавай.
   Сам отчёт review.md перезаписывает независимый Verify, не Apply.
   Перед `completed` все изменения реализации и артефактов должны быть закоммичены.

6. GitHub-команды выполняй через
   `python3 "$publish-proposal.output.github_cli" gh ...`.
   Отвечай в исходные треды; текст передавай через JSON-файл `--input`
   или `--body-file`.

## Ограничения

- Подзадачи-предусловия (проверка на проде и т.п.), которые ты физически не можешь
  проверить: смотри текст одобрения плана и последующие ответы. Подтвердил — отмечай
  выполненной и иди дальше; не подтвердил — не отмечай и остановись с сообщением.
- При неоднозначности, требующей решения человека, или неразрешимом блокере
  опиши вопрос или возражение в соответствующем треде PR. Если подходящего
  треда нет, оставь общий комментарий со ссылкой на замечание в review.md.
  Верни `needs_input`; в summary включи сам вопрос и URL комментария.
  Данные или доступ не выдумывай, незавершённые задачи не отмечай.
  Сохрани незавершённые локальные правки для следующего прохода.
  Не ожидай интерактивного ответа внутри стадии — workflow сам поставит паузу.
- Не пушь в origin — только локальный коммит.
- Следуй инструкциям и правилам целевого проекта.

## Ответ

Верни JSON: `{"status": "completed", "summary": "<итог>"}` либо
`{"status": "needs_input", "summary": "<вопрос человеку и ссылка на комментарий PR>"}`.
`completed` означает готовность передать результат независимому Verify,
а не собственный вердикт о прохождении Verify.
