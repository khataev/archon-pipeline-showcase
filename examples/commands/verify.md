# Verify: изменение `$propose.output.change_name`

Верифицируй OpenSpec-изменение `$propose.output.change_name` против его артефактов
(specs, tasks, design). Действуй по процедуре из `.agents/skills/openspec-verify-change/SKILL.md` —
прочитай этот файл в worktree и следуй ему (сокращённая выжимка ниже).

- PR: $publish-proposal.output.pr_url

## Шаги

1. Сам прочитай актуальные обсуждения этого PR через
   `python3 "$publish-proposal.output.github_cli" gh ...`:
   reviews, общие комментарии и inline-треды со всеми ответами, включая
   устаревшие строки предыдущих версий review.md. Учитывай пагинацию.
   Читай ответы вместе с исходным замечанием.
   Явные исключения, принятые человеком, учитывай при оценке и отрази в отчёте
   со ссылкой на тред; не выдавай их снова за непринятую обязательную доработку.
   Заявление Apply об исправлении само по себе не является подтверждением.
   Проверяй фактический код и актуальные артефакты, в том числе план,
   изменённый Apply по указанию человека.

2. Состояние и контекст:

   ```bash
   openspec status --change "$propose.output.change_name" --json
   openspec instructions apply --change "$propose.output.change_name" --json
   ```

3. Оцени три измерения:
   - **Completeness** — все ли задачи `tasks.md` отмечены `[x]`, покрыты ли
     требования из delta-спеков.
   - **Correctness** — соответствие реализации требованиям и сценариям.
   - **Coherence** — следование design.md и паттернам проекта.

4. Запиши отчёт в `openspec/changes/$propose.output.change_name/review.md`:
   - scorecard по трём измерениям;
   - замечания CRITICAL / WARNING / SUGGESTION со ссылками `file:line`;
   - итоговый вердикт.
   Перезапиши отчёт текущей проверкой, сохраняя смысл принятых исключений
   и ссылки на исходные треды. Код реализации не меняй. Коммит отчёта
   и push выполнит следующий узел перед паузой человека.

## Вердикт (закрытый набор)

- `ready` — нет непринятых CRITICAL, задачи выполнены либо конкретные исключения явно приняты человеком.
- `needs_work` — есть непринятые CRITICAL (незавершённые задачи / нереализованные
  требования / расхождения с spec или design).

## Ответ

Верни JSON-объект ровно такого вида (без лишнего текста):

```json
{"verdict": "ready", "summary": "Краткий итог проверки"}
```

или

```json
{"verdict": "needs_work", "summary": "Краткий список обязательных доработок"}
```
