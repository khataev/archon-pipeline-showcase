# Изучение и адаптация

[← README](../README.md) · [Архитектура](architecture.md)

Откройте `docs/pipeline.html` локально в браузере. Это просмотр документа: он не запускает workflow и не делает сетевых запросов. YAML в `examples/workflow.yaml` — снимок графа с placeholders, с адаптированными командами и скриптами, а не самодостаточный пакет Archon. Не запускайте его без настройки зависимостей и проверки разрешений: исходный граф публикует коммиты и PR, обновляет карточку и вызывает агентов.

## Для переноса в свою среду

1. Установите совместимый Archon и изучите актуальные справки CLI и [документацию Archon](https://archon.diy/llms.txt): синтаксис и поведение версий могут меняться. Понадобятся Git, Python, доступная модель/провайдер, OpenSpec, GitHub CLI и адаптированные навыки агентов; для Explore — Herdr. Planka и планировщик нужны для автоматического intake.
2. Создайте отдельный тестовый репозиторий и свои тестовые доску, пользователя и карточку. Скопируйте конфигурацию в `.archon/config.yaml`, выберите существующую base branch. Разместите `workflow.yaml`, `scripts/` и `commands/` в каталоге `.archon/workflows/<pack>/<workflow>/`, переименовав YAML по имени workflow. Установите необходимые OpenSpec skills в целевом проекте. Замените placeholders моделей и согласуйте схему выводов всех узлов.
3. Настройте секреты вне Git и ограничьте права интеграций. Подготовьте trigger binding с выбранным workflow, идентичностью запуска и ресурсом capacity 1 / overlap queue, если общая среда не выдерживает параллельность. Сверьте точную схему binding с установленной версией Archon; готовая конфигурация не включена.
4. Настройте переменные `PLANKA_FIELD_GROUP_ID`, `PLANKA_STAGE_FIELD_ID`, `PLANKA_RUN_FIELD_ID`, `PLANKA_SKIP_EXPLORE_LABEL_ID`, `PLANKA_TEST_LIST_ID`, `PLANKA_CHANGE_FIELD_ID`, `PLANKA_VERDICT_FIELD_ID`, `EXPLORE_MODEL` и при необходимости `SSH_MACHINE_NAME`. GitHub CLI должен быть авторизован через собственный механизм или переменные `GH_TOKEN` / `GITHUB_TOKEN`; пример не включает частный credential helper. Адаптируйте `examples/poll.py`, укажите идентификаторы своей тестовой доски и путь к binding через окружение. Планировщик на Linux можно подключать только после проверки вручную на тестовых данных. В отличие от источника пример не читает env-файл и не настраивает PATH.
5. Проверьте пакет штатными командами установленной версии: `archon validate workflows <name>`, затем `archon workflow test <name>` с собственными фикстурами и `archon workflow run <name> --dry-run --default-stubs --input card_id=<test-id>`. Dry-run не проверяет реальные сервисы, а флаг `--exec-code` выполняет код и требует отдельной оценки. Сначала проверьте негативные маршруты и границы публикации на изолированном стенде.

Перед реальным запуском проверьте все точки записи, стоимость моделей, область доступа токенов, конкурентность и восстановление после ошибок. Примеры не содержат готовых команд для подключения к реальной доске или публикации.
